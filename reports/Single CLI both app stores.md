# Unify both app store releases today

Two separate release CLIs exist because Apple and Google run fundamentally incompatible release machines, yet one well-scoped single binary can cover both without browser hacks — and no maintained tool does it today. On the Apple side `asc` proves the model with **~60 command families over the App Store Connect API in a single Go binary (7.6k stars, MIT)** ([Source](https://github.com/rorkai/App-Store-Connect-CLI)), while on the Play side `gplay` and `GPC` prove equivalent depth with **250+ and 234 claimed Publisher endpoints respectively** ([Source](https://github.com/tamtom/play-console-cli)) ([Source](https://github.com/yasserstudio/gpc)). The only maintained cross-store incumbent is **fastlane at 42.2k stars shipping monthly through 2.240.1 in September 2026** ([Source](https://github.com/fastlane/fastlane/releases)), still Ruby-bound and volunteer-run, while every modern alternative covers one store, embeds in one build system, or lives behind a hosted dashboard. That leaves a crisp opening: a Go single-binary CLI that unifies auth profiles, a cross-store readiness gate, and staged-rollout orchestration, distributed from day one via Homebrew plus an agent skill and MCP server as **Expo and Runway have already validated** ([Source](https://docs.expo.dev/deploy/submit-to-app-stores/)) ([Source](https://www.runway.team/pricing)).

## Apple and Google force two different release machines

Apple's release surface is a broad API-resource sprawl plus an orchestration layer, which is why its CLI grew to **~60 top-level families from `apps` and `versions` through `testflight`, `signing`, `subscriptions` to high-level `publish`, `validate` and `release`** ([Source](https://github.com/rorkai/App-Store-Connect-CLI/blob/main/docs/COMMANDS.md)). The canonical path composes granular calls into **`asc publish appstore --app … --ipa … --version … --submit --confirm` with `release stage --dry-run`, `validate` readiness and `status --watch` monitoring** ([Source](https://github.com/rorkai/App-Store-Connect-CLI)). Google's surface is narrower but transactionally alien: the Publishing API automates **"uploading new versions," "assigning APKs to various Tracks (alpha, beta, staged rollout, or production)" and "creating and modifying listings, including localized text and graphics"** ([Source](https://developers.google.com/android-publisher)), bundled as **a single draft edit committed atomically with only one open edit per user** ([Source](https://developers.google.com/android-publisher)) ([Source](https://developers.google.com/android-publisher/edits)). Staged rollouts ride **`inProgress` with `userFraction`, `halted`, `completed` and `draft` states with halt/resume semantics** ([Source](https://developers.google.com/android-publisher/tracks)), form-factor tracks are **prefixed (`wear:production`, automotive, tv) alongside `production`, `beta` and `qa`** ([Source](https://developers.google.com/android-publisher/tracks)), and release notes attach **per-release via `releaseNotes` language/text** ([Source](https://developers.google.com/android-publisher/tracks)).

Auth hardens the split. Apple uses **self-contained JWT API keys where team keys need key ID plus issuer ID plus `.p8` and individual keys need key ID plus `.p8`** ([Source](https://github.com/rorkai/App-Store-Connect-CLI)), generated by an Admin with **roles mirroring user roles and team keys spanning all apps** ([Source](https://developer.apple.com/documentation/appstoreconnectapi/creating-api-keys-for-app-store-connect-api)), stored by default in the **system keychain with config-file and `ASC_KEY_ID`/`ASC_ISSUER_ID`/`ASC_PRIVATE_KEY_B64` env fallbacks for CI** ([Source](https://raw.githubusercontent.com/rorkai/App-Store-Connect-CLI/main/authentication.mdx)). Play is identity-based and two-sided: **create a Cloud project, enable the API, mint a service account or OAuth client** ([Source](https://developers.google.com/android-publisher/getting_started)), where the service account is the **recommended server-to-server path whose key must never be exposed** ([Source](https://developers.google.com/android-publisher/getting_started)) and must **additionally be invited under Play Console Users & Permissions** ([Source](https://developers.google.com/android-publisher/getting_started)), with **OAuth for per-user delegation gated by consent-screen branding** ([Source](https://developers.google.com/android-publisher/getting_started)). Since the December 2025 docs **no Cloud-project link is needed for API access** ([Source](https://developers.google.com/android-publisher/getting_started)), but the Console invite remains the irreducible manual step that both **`gplay setup --auto` and `gpc setup` automate everything except** ([Source](https://github.com/tamtom/play-console-cli)). Operationally Apple gives bearer keys with embedded roles while Play gives Cloud credentials plus Console grants, which is why setup guides, secret shapes, CI wiring and least-privilege stories cannot share code paths today.

The Console-only remainder differs too. Apple reserves **App Privacy publication, app creation and review-center actions for web sessions because "the public API cannot verify whether App Privacy is fully published"** ([Source](https://skillshub.wtf/rudrankriyam/app-store-connect-cli-skills/asc-submission-health)), tracked as **open web-session issues #2275–#2301 with live inventory in `asc capabilities --status web-session`** ([Source](https://raw.githubusercontent.com/rorkai/App-Store-Connect-CLI/main/docs/PARITY.md)). Google reserves **app birth plus first artifact, publish/unpublish flips and legal consents** ([Source](https://developers.google.com/android-publisher/edits)), where **new apps and first APKs are Console-only** ([Source](https://developers.google.com/android-publisher/edits)) echoed by **GPP, supply and GPC each requiring a manual first upload** ([Source](https://github.com/Triple-T/gradle-play-publisher)) ([Source](https://docs.fastlane.tools/actions/supply/)) ([Source](https://github.com/yasserstudio/gpc)), plus **ordinary Google-managed signing enrollment, listing experiments and policy questionnaires** ([Source](https://github.com/tamtom/play-console-cli)) ([Source](https://raw.githubusercontent.com/tamtom/play-console-cli/main/docs/policy-safe-automation.md). The notable Play exception is that **Data safety gains a write-only `POST applications/{packageName}/dataSafety` with no read-back** ([Source](https://developers.google.com/android-publisher/api-ref/rest)), which breaks idempotent diffing by design. Two CLIs therefore persist not from taste but from incompatible auth planes, incompatible release transactions, and non-overlapping Console-only edges.

## One binary can speak both store languages safely

A unified CLI is feasible because roughly 95% of repeat releases on both sides already sit on public, unattended-safe APIs, with the web-only remainder cleanly severable as guided handoffs. On Apple the pattern is proven: unattended JWT auth covers nearly everything while **`asc web` acts as an explicitly experimental bridge driving private `/iris` endpoints only where no public API exists** ([Source](https://docs.asccli.sh/commands/web)), logging in via **SRP plus 2FA with file-backed or keychain-cached sessions exportable for CI** ([Source](https://raw.githubusercontent.com/rorkai/App-Store-Connect-CLI/main/authentication.mdx)) to run **`web privacy catalog|pull|plan|apply|publish` as `pull → plan → apply --confirm → publish --confirm`** ([Source](https://docs.asccli.sh/commands/web)). That bridge carries stated costs of **1-second minimum request spacing, auth churn, contract drift and account-risk disclaimers** ([Source](https://deepwiki.com/rorkai/App-Store-Connect-CLI/3.3-web-session-authentication)) ([Source](https://docs.asccli.sh/commands/web)), and `asc` deliberately keeps deep checks advisory so **unavailable private endpoints report `unverified` rather than blocking unless `--strict`** ([Source](https://github.com/rorkai/App-Store-Connect-CLI)). On Play no bridge is needed or wanted: `gplay` draws the opposite safety line with **`capabilities` classifying workflows as official/manual/unsupported, `bootstrap plan` never executing, and no private endpoints or browser automation** ([Source](https://raw.githubusercontent.com/tamtom/play-console-cli/main/docs/policy-safe-automation.md)). A unified tool should copy the `gplay` posture by default and treat any `web` bridge as an explicitly gated Apple-only extra, not the core.

Feasibility also rests on both sides already converging on the same operator contract. Apple ships **`auth status --validate` and `auth doctor --fix --confirm`, fresh-runner signing as `signing fetch --create-missing` through `signing sync push/pull` (Git, S3 with OIDC, experimental GitLab/AWS) to `keychain install`, `profiles install`, `xcode signing plan/apply`, `archive/export` and `keychain delete`** ([Source](https://github.com/rorkai/App-Store-Connect-CLI/blob/main/docs/CI_CD.md)), officially supported on **GitHub Actions, GitLab, Bitrise and CircleCI** ([Source](https://github.com/rorkai/App-Store-Connect-CLI/blob/main/docs/CI_CD.md)). Play mirrors it with **`gplay auth doctor` plus multi-account profiles** ([Source](https://github.com/tamtom/play-console-cli)) and **GPC's four auth methods plus `auth profiles/switch/whoami`, `doctor` with 20+ checks, semantic exits 0–6 and `--dry-run` on every write** ([Source](https://github.com/yasserstudio/gpc)). Apple binds automation with **per-key rolling-hour limits surfaced in `X-Rate-Limit` with 429 plus `RATE_LIMIT_EXCEEDED`, GET-only retries honoring Retry-After** ([Source](https://developer.apple.com/documentation/appstoreconnectapi/identifying-rate-limits)) ([Source](https://github.com/rudrankriyam/App-Store-Connect-CLI/blob/main/docs/API_NOTES.md)), while Play binds it with the single-open-edit invalidation rule that **any Console change or committed edit invalidates all other edits** ([Source](https://developers.google.com/android-publisher/edits)) and **commit-time managed-publishing routing that forced supply's `changes_not_sent_for_review` plus auto-rescue flag** ([Source](https://docs.fastlane.tools/actions/supply/)). None of this requires inventing protocols; it requires one command tree that maps `release`, `status`, `validate`, `doctor` and `diff` onto two backends with per-store auth resolution, per-store dry-run, and honest `manual-handoff` states.

The build-versus-Xcode-Cloud question resolves the same way. Xcode Cloud remains **Apple-ecosystem only with ephemeral Apple-silicon builders and GitHub/Bitbucket/GitLab cloning** ([Source](https://developer.apple.com/xcode-cloud/)), offering **only three `ci_*` scripts, no arbitrary step graph, no `sudo`, and Apple-dictated toolchains** ([Source](https://dodecaidr.pro/en/articles/xcode-cloud-2026-guide/)), with **no self-hosted runners and env-var-only secrets** ([Source](https://dodecaidr.pro/en/articles/xcode-cloud-2026-guide/)). It exposes **API plus webhooks for external orchestration** ([Source](https://developer.apple.com/videos/play/wwdc2022/110375/)), which `asc` already uses via **`xcode-cloud run` and `build-runs get`** ([Source](https://github.com/rorkai/App-Store-Connect-CLI)). A unified CLI therefore should not replace Xcode Cloud but drive it as one specialized iOS worker from a shared external pipeline that also drives Play-side CI.

## Fastlane stands alone as rivals cover half the job

The verified landscape is stark: fastlane is the only maintained unified iOS-plus-Android release CLI, and everything else is half a tool or a hosted service. Fastlane holds **42.2k stars with regular monthly 2.234.0–2.240.x releases into September 2026** ([Source](https://github.com/fastlane/fastlane/releases)) covering both stores via **`deliver` for App Store, `supply` for Play, plus `pilot`, `snapshot`/`screengrab`, `precheck` and `match`** ([Source](https://github.com/fastlane/fastlane)) ([Source](https://docs.fastlane.tools/), yet it **requires Ruby 3.2+ and Bundler/Homebrew/RubyGems after dropping 2.7 and 3.0** ([Source](https://docs.fastlane.tools/)) on a **volunteer, OpenCollective-funded footing** ([Source](https://github.com/fastlane/fastlane/releases)). The strain narrative is real but needs nuance: the tracker shows **42,201 stars, 6,037 forks and 665 combined open issues/PRs with a push on 2026-10-03** ([Source](https://api.github.com/repos/fastlane/fastlane)), the "is this project dead" thread documents **Ruby 3.4 unusable for a year and funding fragility** ([Source](https://github.com/fastlane/fastlane/issues/29713)), revival came via **volunteer CI fixes and 2.229.0** ([Source](https://github.com/fastlane/fastlane/issues/29713)), and current Apple lanes still function but brittlely with **`deliver` nil-crashes fixed point-to-point and Xcode 26.x agreement/upload churn** ([Source](https://github.com/fastlane/fastlane/issues/29983)) ([Source](https://github.com/fastlane/fastlane/issues/29971)), to the point a maintainer advises **moving to API keys because username/password has little future** ([Source](https://github.com/fastlane/fastlane/issues/29919)).

Against that incumbent the modern single-store CLIs are deep but deliberately half-scoped. On Apple `asc` is **Go, MIT, single-binary via Homebrew, install script and WinGet with no toolchain needed** ([Source](https://github.com/rorkai/App-Store-Connect-CLI)) and explicitly declares **Android tooling, lane runtimes, extra chat connectors and doc generators as non-goals** ([Source](https://raw.githubusercontent.com/rorkai/App-Store-Connect-CLI/main/docs/PARITY.md)). On Play `gplay` is **Go single-binary at 252 stars and 343 commits claiming 250+ commands across 9 Google APIs with all 145 Publisher methods mapped** ([Source](https://github.com/tamtom/play-console-cli)), bundling **one-command rollout releases, subscriptions and offers, purchase verification and refunds, vitals, review replies, reports, user grants, Managed Play, Checks gating, 9 offline preflight scanners, Fastlane interop and `--dry-run` on every write** ([Source](https://github.com/tamtom/play-console-cli)), while **GPC at 86 stars and 741 commits claims 234 publisher endpoints as a TypeScript monorepo installable via npm, brew or standalone binary** ([Source](https://github.com/yasserstudio/gpc)) with **rollout increase/halt, `--validate-only`, Fastlane-compatible listings, 500-char changelog plus BYO-key AI translation, `status`, crash-gated `watch`, exit-code vitals gates, reviews, Managed Play, games CRUD, 9 preflight scanners and bundle analyze** ([Source](https://github.com/yasserstudio/gpc)). Both mark **supply at roughly 20 endpoints with no subscriptions depth, verification, vitals, reviews or Managed Play** ([Source](https://github.com/tamtom/play-console-cli)) ([Source](https://github.com/yasserstudio/gpc)), and `supply` itself confirms the ceiling by covering **upload, tracks, rollouts, listings, changelogs and promotion** ([Source](https://docs.fastlane.tools/actions/supply/)) while demanding **manual first-build setup** ([Source](https://docs.fastlane.tools/actions/supply/)) and absorbing API drift like **auto-retired `check_superseded_tracks` and `deactivate_on_promote`** ([Source](https://docs.fastlane.tools/actions/supply/)). Gradle Play Publisher fills the Android-native niche at **4.3k stars and 349 forks with `publishPaidReleaseBundle`-style tasks, flavor-to-track mapping and internal-sharing URLs** ([Source](https://github.com/Triple-T/gradle-play-publisher)) but declares **maintenance mode where issues are ignored** ([Source](https://github.com/Triple-T/gradle-play-publisher)) and still needs **Console first-upload, signed builds and a service account** ([Source](https://github.com/Triple-T/gradle-play-publisher)).

Hosted and framework-adjacent players confirm willingness to pay without closing the local-CLI gap. **EAS Submit uploads to both stores from any OS with `--non-interactive`** ([Source](https://docs.expo.dev/deploy/submit-to-app-stores/)) yet **explicitly does not manage metadata, screenshots or notes with Metadata still in preview** ([Source](https://docs.expo.dev/deploy/submit-to-app-stores/)). **Bitrise CLI at 901 stars runs workflows locally but submits via cloud Steps** ([Source](https://github.com/bitrise-io/bitrise)), **Codemagic splits into separate `app-store-connect` and `google-play` executables** ([Source](https://github.com/codemagic-ci-cd/cli-tools)), **Runway is a hosted dashboard whose CLI/API and MCP sit on paid tiers** ([Source](https://www.runway.team/pricing)), and **Tramline is a self-hosted Rails app at 407 stars, not a CLI** ([Source](https://github.com/tramlinehq/tramline)) ([Source](https://www.tramline.app/pricing)). Pricing anchors cluster tightly at **Tramline Team $50/app/month, Expo $19–$199/month plus per-build overage, Runway per-app custom** ([Source](https://www.tramline.app/pricing)) ([Source](https://expo.dev/pricing)) ([Source](https://www.runway.team/pricing)), against **fastlane free on donations** ([Source](https://github.com/fastlane/fastlane)), which supports an open-core local CLI plus paid hosting in the $19–$50 band. Pain data points the same direction: Apple's blockers are **crashes, incomplete metadata, missing demo accounts, dead backends and review notes** ([Source](https://developer.apple.com/app-store/review/guidelines/)) with **placeholder and screenshot-mismatch rejection rules** ([Source](https://developer.apple.com/app-store/review/guidelines/)), while `precheck` covers only a **crowdsourced text-rule subset (sentiment, swears, other-platform mentions, dead URLs, placeholders, future claims) that is iOS-only** ([Source](https://docs.fastlane.tools/actions/precheck/)) and even **invites users to file rejections to grow the rules** ([Source](https://docs.fastlane.tools/actions/precheck/)).

## Unify around readiness, rollout and safe auth

The architecture that falls out of both stores is a single Go binary with two store adapters behind one operator vocabulary, copying what each side already proved. Model Apple on `asc`'s resource-plus-verb taxonomy and high-level **`publish`, `validate`, `release stage`, `submit` and `status`** composition ([Source](https://github.com/rorkai/App-Store-Connect-CLI/blob/main/docs/COMMANDS.md)) ([Source](https://github.com/rorkai/App-Store-Connect-CLI)), and model Play on the transactional **edit → tracks → listings → monetization → reviews → commit** chain with **immediate-effect purchase and refund methods outside edits** ([Source](https://developers.google.com/android-publisher/edits)) ([Source](https://developers.google.com/android-publisher/api-ref/rest). Auth needs two credential planes under one profile switcher: Apple JWT with **keychain default and env/config fallbacks plus `auth status` and `auth doctor`** ([Source](https://raw.githubusercontent.com/rorkai/App-Store-Connect-CLI/main/authentication.mdx)) ([Source](https://github.com/rorkai/App-Store-Connect-CLI)), and Play service-account JSON plus **Workload Identity Federation, least-privilege Console roles and ADC with impersonation** ([Source](https://docs.fastlane.tools/actions/supply/)) ([Source](https://github.com/Triple-T/gradle-play-publisher)) fronted by a **`setup --auto` that automates everything except the Console invite and a `doctor` that verifies it** ([Source](https://github.com/tamtom/play-console-cli)) ([Source](https://github.com/yasserstudio/gpc)). Ship the safety contract both tools converged on: **`capabilities` as a live coverage catalog including web-only and manual rows** ([Source](https://github.com/rorkai/App-Store-Connect-CLI/blob/main/docs/COMMANDS.md)) ([Source](https://raw.githubusercontent.com/tamtom/play-console-cli/main/docs/policy-safe-automation.md)), **`--dry-run` and `--validate-only` on every write** ([Source](https://github.com/tamtom/play-console-cli)) ([Source](https://github.com/yasserstudio/gpc)) ([Source](https://docs.fastlane.tools/actions/supply/), **`status` dashboards and `watch` monitors with crash-gated auto-halt** ([Source](https://github.com/yasserstudio/gpc)), **TTY-aware JSON by default in pipes with table and markdown options** ([Source](https://github.com/rorkai/App-Store-Connect-CLI/blob/main/docs/COMMANDS.md)), and **Fastlane metadata interop plus `bootstrap` pull and minified JSON** ([Source](https://github.com/tamtom/play-console-cli)) ([Source](https://github.com/Triple-T/gradle-play-publisher)) so teams migrate incrementally. Distribute the way 2026 expects: **Homebrew and standalone binaries for humans and CI** ([Source](https://github.com/rorkai/App-Store-Connect-CLI)) ([Source](https://github.com/yasserstudio/gpc)) alongside a **pinned, verifiable 25-skill pack installed via `install-skills`** ([Source](https://github.com/rorkai/App-Store-Connect-CLI)) with **`search`, `schema`, `docs` and `init` self-documentation for agents** ([Source](https://github.com/rorkai/App-Store-Connect-CLI/blob/main/docs/COMMANDS.md)), plus an MCP server and skill on day one because **Expo ships `eas-app-stores` plus MCP on every tier** ([Source](https://docs.expo.dev/deploy/submit-to-app-stores/)) ([Source](https://expo.dev/pricing)) and **Runway gates MCP and its Claude connector to paid tiers** ([Source](https://www.runway.team/pricing)).

### Solve cross-store readiness and staged rollout first

The one concrete problem to solve is the cross-store release-readiness gate with staged-rollout spine, because it is the only workflow every team repeats, both stores punish, and no incumbent owns. Today readiness is **Apple's human checklist plus iOS-text-only `precheck`** ([Source](https://developer.apple.com/app-store/review/guidelines/)) ([Source](https://docs.fastlane.tools/actions/precheck/)) and **reactive EAS log-scraping after upload** ([Source](https://docs.expo.dev/deploy/submit-to-app-stores/)), while rollout lives in **two consoles with incompatible fraction, halt and draft semantics** ([Source](https://developers.google.com/android-publisher/tracks)) ([Source](https://docs.fastlane.tools/actions/supply/)). Build `release check` to lint binary plus metadata plus policy plus rollout config in one pass — screenshot presence per locale, privacy and Data-safety answers, subscription attachment, track fractions, review-note completeness — then `release stage`, `release go`, `release halt` and `status --watch` to move both stores together with per-store dry-run and a single `manual-handoff` exit where Console clicks remain. Price the local binary free and open-core like **Tramline Apache-2.0 plus hosted tiers** ([Source](https://github.com/tramlinehq/tramline)) ([Source](https://www.tramline.app/pricing)) toward the validated band.

The spike to de-risk it runs as a tight two-week vertical slice rather than a feature survey. Start by auditing both discovery surfaces live, pinning `asc capabilities` against the App Store Connect schema and the Publisher discovery document against `gplay`'s schema check, specifically to resolve the **Data-safety write-only scope, managed-publishing flags and experiment absence** ([Source](https://developers.google.com/android-publisher/api-ref/rest)) ([Source](https://raw.githubusercontent.com/tamtom/play-console-cli/main/docs/policy-safe-automation.md). Then prototype dual auth against throwaway apps using **Apple env-key CI auth and Play service-account plus Console invite with `doctor` on both** ([Source](https://raw.githubusercontent.com/rorkai/App-Store-Connect-CLI/main/authentication.mdx)) ([Source](https://developers.google.com/android-publisher/getting_started)), proving least-privilege roles and keychain-free CI. Then implement only `release check`, `release stage --dry-run`, `release go --track internal`, `status` and `watch` against one real internal track and one TestFlight group, with **single-edit serialization, `changesNotSentForReview` rescue and Apple rate-limit retry** ([Source](https://developers.google.com/android-publisher/edits)) ([Source](https://docs.fastlane.tools/actions/supply/)) ([Source](https://developer.apple.com/documentation/appstoreconnectapi/identifying-rate-limits)) built in and every Console-only encounter returning a scripted handoff URL instead of failing opaquely. Success is a demo where one command stages the same build number, lints both listings, holds for approval, rolls to a fraction on both stores, and halts both on a vitals breach — the hosted-automation value of **Runway-style submit, phased-rollout and translation automations** ([Source](https://www.runway.team/pricing)) delivered as a local binary teams already know how to install.

## Conclusion

The split-CLI world is an accident of incompatible store APIs hardened into incompatible auth, transaction and Console-boundary habits, not a law of nature. Treating the Apple adapter as the breadth model, the Play adapters as the transaction-safety model, and fastlane as a caution on Ruby and volunteer bus-factor turns unification from a rewrite fantasy into an integration job with a priced open-core path. Winning means refusing the browser-automation trap, making every Console limit explicit and scriptable around, and proving the readiness-plus-rollout spine on real tracks before expanding to monetization, reviews and vitals.
